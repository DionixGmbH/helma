# Embedded Database

When a prototype has no `type.properties` (or no `_db`), its HopObjects are persisted to Helma's **embedded XML database**. This is useful for getting started without setting up a SQL server and for storing small or session-scoped data.

## Storage Layout

By default, the embedded DB lives at `db/<appname>/`. Each Node is one XML file:

```
db/
└── blog/
    ├── 1.xml             ← root node
    ├── 2.xml             ← children of root
    ├── 3.xml
    ├── ...
    └── idgen.xml         ← internal counter
```

Each `<id>.xml` looks like:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<xmlroot xmlns:hop="http://www.helma.org/docs/guide/features/database">
  <hopobject id="2" name="alice" prototype="User" created="1719000000" lastmodified="1719000123">
    <hop:child idref="3" prototyperef="Post" nameref="hello-world"/>
    <hop:child idref="4" prototyperef="Post" nameref="another"/>
    <hop:parent idref="1" prototyperef="Root"/>
    <hop:property name="email"><![CDATA[alice@example.com]]></hop:property>
    <hop:property name="bio"><![CDATA[A blog about cats.]]></hop:property>
    <hop:property name="signupAt"><hop:date>1718900000</hop:date></hop:property>
    <hop:property name="role"><hop:int>1</hop:int></hop:property>
  </hopobject>
</xmlroot>
```

Properties are stored as typed elements — `<hop:int>`, `<hop:date>`, `<hop:float>`, `<hop:string>` (with CDATA), `<hop:node>`.

## Reading & Writing

From JavaScript:

```javascript
// Create a new node
var post = new Post();        // Post has no type.properties
post.title = "Hello";
post.body  = "Long...";
root.add(post);               // becomes a child of root

// Walk the tree
root.size();                  // number of root's children
root.get(0);                  // first child
root.get("hello-world");      // by name (element name)

// Iterate
for each (var post in root.list()) {
    res.write(post.title);
}
```

The HopObject API is identical to relational HopObjects.

## ID Generation

For embedded-DB-backed prototypes, IDs are generated by `XmlIDGenerator`:

- Stored in `db/<appname>/idgen.xml`
- Monotonically increasing integers
- Resilient against crashes — the counter file is rewritten on each request

To use `[uuid]` instead, set `_idgen = [uuid]` even on prototypes without `_db`. The UUID is still stored in the embedded file but the ID format is the UUID string.

## Flushing & Durability

Writes are buffered in memory until `Transactor.commit()`:

1. Modified nodes are serialized to XML
2. Files are written via `XmlDatabase.commit()` to the on-disk location
3. The transaction is durable when the JVM's filesystem sync completes

There is no journaling — a crash during write may leave a partial file. Helma re-reads from disk on next startup; corrupt files are reported in the log and may need manual repair.

## Migration: Embedded → Relational

To move a prototype from embedded to relational:

1. Create the table in your SQL DB (with the right columns).
2. Add `type.properties` to the prototype directory.
3. Write a migration script:
    ```javascript
    function migratePosts() {
        var srcRoot = ... // somehow access old root via SQL-bypass
        for each (var post in srcRoot.posts.list()) {
            var newP = new Post();
            newP.title = post.title;
            newP.body = post.body;
            // ... etc.
            root.posts.add(newP);
        }
    }
    ```

Helma doesn't have a built-in migration tool. The recommended path is to write the script once, dual-write during cutover, then switch reads.

## Performance

The embedded DB is **slow** compared to a real SQL DB:

- One file per Node = filesystem overhead for many small files
- Linear scans to find Nodes by content (no indexes)
- No concurrent multi-Node writes

Use it for:

- Small datasets (< 10k nodes)
- Configuration / settings storage
- Sessions (`persistentSessions = true`)
- Caches and counters that don't need durability

Don't use it for:

- High-traffic data (posts, comments, etc.)
- Large blob storage (use disk + reference)
- Anything you need to query by content efficiently

## Inspecting the Embedded DB

```bash
# List all files
ls db/myapp/

# Pretty-print one
xmllint --format db/myapp/2.xml
```

Or use the management UI's database browser (in `manage`).

## Configuration

```properties
# app.properties
dbdir = db/myapp        # override the default location (relative to helma.home)

# Or, server-wide:
# server.properties
dbhome = /var/lib/helma/db
```

## Sessions in the Embedded DB

When `persistentSessions = true`:

```properties
persistentSessions = true
```

Sessions are serialised to `db/<appname>/sessions` on shutdown and restored on startup. The serialization uses Helma's `ScriptableOutputStream` so JS objects within `session.data` survive — provided they're serializable.

## Backup & Restore

```bash
# Backup
cp -r db/myapp /backups/myapp-$(date +%Y%m%d)

# Restore — Helma must be stopped
rm -rf db/myapp
cp -r /backups/myapp-20260601 db/myapp
```

For incremental backup, rsync the `db/` directory. The XML files are stable on disk — no journaling means no in-flight writes.
